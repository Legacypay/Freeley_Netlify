# netlify/functions/

## Purpose
22 Netlify serverless functions (`exports.handler = async (event) => {...}`) forming the entire backend API for Freeley, a telehealth marketing site selling compounded GLP-1/weight-loss, longevity/peptide, hair-loss, and sexual-wellness prescriptions via telehealth. Responsibilities split into five groups: (1) checkout/payment via Stripe or Authorize.Net, (2) submitting patient intake to MD Integrations (MDI, the telehealth/EHR partner) and tracking case status, (3) Supabase-authenticated "patient hub" endpoints (messaging, billing, case details), (4) inbound webhooks from Stripe and MDI, and (5) three scheduled/cron jobs. All functions are called from the frontend at `/.netlify/functions/<name>`.

## For AI Agents
### Working In This Directory
- All files use CommonJS (`require`/`exports.handler`), not ESM — consistent with `"type": "commonjs"` in the repo's `package.json`.
- **Auth pattern**: any function touching patient data (case status, messages, billing, encounter details, patient token) requires a Supabase access token in `Authorization: Bearer <token>`, verified via `lib/verify-supabase-token.js`. Unauthenticated requests get `401`. Note `lib/verify-firebase-token.js` also exists (legacy Firebase Auth verifier) but none of the current 21 functions call it — Supabase Auth has fully replaced Firebase for this flow.
- **Two identities are distinguished per call**: the Supabase-authenticated site user (proves *who is asking*) vs. the MDI `patient_id`/patient email (the actual telehealth record, which may differ from the Supabase login email — see `getPatientToken.js`'s email-resolution fallback chain).
- **CORS pattern**: two conventions coexist. Newer/most functions call `getCorsHeaders(event)` from `lib/mdi-client.js` (echoes back `https://freeley.com` or `https://www.freeley.com`, else defaults to the first). A few older ones (`caseStatus.js`, `getBillingHistory.js`, `getEncounterDetails.js`, `patientCases.js`, `submitQuiz.js`) use the static `CORS_HEADERS` export from the same module instead — functionally similar but doesn't vary by request origin. `create-payment-intent.js`/`create-authnet-transaction.js` build their own origin-allowlist headers inline rather than importing from `lib/mdi-client.js`.
- **OPTIONS preflight**: every function that's called from the browser (not webhooks, not scheduled jobs) handles `OPTIONS` explicitly, returning `204` with CORS headers before the method check.
- **Error handling**: outer `try/catch` per handler; errors are logged with a `[BRACKETED TAG]` prefix (e.g. `[SUBMIT QUIZ]`, `[STRIPE WEBHOOK]`) via `console.log`/`console.error`/`console.warn`, and the client gets a generic message — internal error detail is never leaked in the response body. Webhook handlers (`stripeWebhook.js`, `mdiWebhook.js`) deliberately return `500` on failure (not `200`) so the sender retries delivery; all other handlers return `200`/`4xx` even for internal failures where retry isn't wanted (e.g. `track-conversion.js` always 200s to never block the patient flow).
- **PHI handling**: any payload containing patient medical data (`submitQuiz.js`, `savePendingCase.js`, `retryPendingCases.js`) is validated with `lib/validate-quiz.js` and encrypted at rest with `lib/phi-crypto.js` (AES-256-GCM) before being written to Netlify Blobs. Internal alerts fired via n8n (`notifyInternalWebhook` in `mdiWebhook.js`, `checkAdditionalApprovals.js`) intentionally carry only opaque `case_id`/`patient_id` — never `patient_email` or message content — per MDI's explicit "do not share patient-identifiable information [in Slack]" guidance; the case/encounter ID is the one identifier MDI has confirmed is safe to share externally.
- **Netlify Blobs stores in use**: `mdi-orders` (voucher/order ↔ patient tracking, keyed by voucher_id), `pending-mdi-cases` (failed-submission retry queue, PHI-encrypted), `mdi-orphaned-vouchers` (2xx MDI responses whose voucher id couldn't be parsed), `mdi-config` (cached MDI tag id), `mdi-approval-alerts` (dedup for `checkAdditionalApprovals.js`), `rate-limits` (sliding-window IP rate limiting).
- **The waitlist gate** (see `../AGENTS.md`) is implemented entirely in `netlify.toml`, not in this directory — no function here contains gating logic. All functions remain reachable via the `/.netlify/functions/*` allow-rule regardless of gate state.

### Testing Requirements
- `npm run test:unit` (= `npm test`, `node --test tests/unit/**/*.test.js`) covers `lib/mdi-voucher.js`, `lib/mdi-tags.js`, and `checkAdditionalApprovals.js`. `npm run test:mdi` (`playwright.functions.config.ts` + `tests/functions/`) is a separate, slower suite that hits the real MDI API through `submitQuiz.js` running under `netlify dev` — see `docs/MDI_TESTING.md`. No automated tests target the other handlers.
- `health.js` is the standard smoke-test endpoint.
- When changing a function, manually exercise it with `netlify dev` (`npm run dev:netlify`) and check the structured console logs for its `[TAG]` prefix.

### Common Patterns
- Price is always computed server-side from `../../pricing.json` (repo root) in both payment-creation functions — the client never sends a dollar amount, preventing price tampering.
- MDI product/questionnaire/offering IDs are centralized in `lib/products.js`; functions never hardcode them. Same rule for the other MDI-side ids/config — `MDI_PARTNER_ID`, `MDI_SANDBOX_ENV_ID`/`MDI_LIVE_ENV_ID` (`lib/mdi-voucher.js`, and duplicated in `lib/mdi-client.js`'s `resolveMdiEnvironment` — see below), `MDI_TEST_TAG_KEY`/`MDI_TEST_TAG_NAME`/`MDI_TEST_TAG_COLOR` (`lib/mdi-tags.js`), `MDI_APPROVAL_CHECK_STATUSES` (`checkAdditionalApprovals.js`) — all read from env with a same-value fallback default, never a bare literal in the hot path. See the env var block at the top of `netlify.toml`.
- MDI test-vs-live is decided in one place for voucher *creation*, `lib/mdi-voucher.js` (`resolveTestMode`), used by `submitQuiz.js` and `retryPendingCases.js`. **Safe by default:** vouchers are test vouchers (`demo: true` + `metadata: "TEST CASE | …"`) unless `MDI_LIVE_MODE=true` **and** `MDI_ALLOW_LIVE_ORDERS=true`. `MDI_FORCE_TEST=true` is the kill switch; `MDI_TEST_EMAIL_PATTERNS` keeps QA emails as tests; a caller can also force test mode explicitly with `is_test: true` in the `submitQuiz` body (validated in `lib/validate-quiz.js`); `MDI_TEST_FULL_FLOW=true` creates a real (tagged) case instead of a demo voucher, and `mdiWebhook.js` attaches the global `test-case` tag via `lib/mdi-tags.js`. `retryPendingCases.js` honors the `is_test` stamped on the queued record at submit time rather than re-resolving from (possibly since-changed) env vars — a queued test can never be silently promoted to a billable live retry. A second, independent env-id helper, `resolveMdiEnvironment({ isTest })` in `lib/mdi-client.js`, is used only by `savePendingCase.js` to stamp `environment` on a freshly-queued record (informational; the actual live/test *decision* on retry is `resolveTestMode`, not this field) — not yet unified with `lib/mdi-voucher.js`, flagged as a follow-up. `mdiWebhook.js`'s `sendPatientEmail` skips test/sandbox orders entirely. See `docs/MDI_TESTING.md` and `docs/MDI_GO_LIVE_OPERATIONS.md`.
- "Approved (Action Required)" per MDI's go-live guidance is handled two ways, deliberately kept independent: (1) `mdiWebhook.js`'s `case_approved` webhook event is treated as the action-required signal — the "your prescription has been approved" patient email is paused, and the internal alert is `severity: high` with the encounter URL; (2) `checkAdditionalApprovals.js` (hourly cron) independently polls the *documented* `is_additional_approval_needed` case flag via `POST /v1/partner/cases/status/:status` and alerts once per case. Neither assumes it's redundant with the other — webhook delivery isn't guaranteed, and it was never confirmed with MDI that `case_approved` and `is_additional_approval_needed` are the same underlying event, so (2) is the confirmed-correct fallback if (1) never fires.
- Conversion tracking (Meta CAPI + GA4) is fired server-side post-payment (primarily from `stripeWebhook.js` and `create-authnet-transaction.js`), never trusting client-only pixels, and strips medical content down to a generic "Telehealth Medical Consultation" label for HIPAA safety.
